# DCON 技術審査会 想定回答

この回答は、2026-05-02 時点の Kotonoha リポジトリ実装に基づく。審査では「実装済み」「デモ版の割り切り」「本番化時の拡張」を分けて説明する。

## システム全体・設計思想

1. なぜ「盆栽と会話する」という形式にしたのですか？
   - 植物管理は数値やアラートだけだと継続しにくいため、日々の世話を「関係性」として続けられる体験にしたかったからです。盆栽の状態を会話に変換することで、水や光への注意を自然に習慣化できます。

2. センサ値をそのまま表示するだけではなく、LLMで会話に変換する価値は何ですか？
   - センサ値は正確ですが、初心者には「何をすればよいか」が分かりにくいです。LLMで現在の水分・光・温度・過去の会話を統合し、短い言葉に変換することで、ユーザーが行動に移しやすくなります。

3. 既存の植物管理アプリとの差別化はどこですか？
   - 単なる管理表やリマインダーではなく、ESP32 の実世界データ、長期記憶、LLM 会話、Web Push による自発メッセージを組み合わせている点です。植物を「管理対象」ではなく「反応する相手」として扱う体験が差別化です。

4. このシステムの一番の技術的な新規性はどこですか？
   - センサ値をプロンプトの一部にするだけでなく、会話履歴を pgvector で長期記憶化し、現在の身体状態・過去の記憶・ユーザー設定を組み合わせて返答を生成する点です。さらに水やりや乾燥イベントでは盆栽側から自発的に話しかけます。

5. ユーザーにとって最も重要な体験価値は何ですか？
   - 「世話を忘れない」だけでなく、「世話が届いたと感じられる」ことです。水をあげた直後に反応が返ってくることで、ユーザーの継続意欲と愛着が生まれます。

6. なぜ対象を一般的な観葉植物ではなく盆栽にしたのですか？
   - 盆栽は長期間の手入れ、個体への愛着、静かな時間の積み重ねと相性がよい対象だからです。会話や記憶の設計も、短期的な成長より「少しずつなじむ」体験に合っています。

7. 「かわいい」「面白い」だけで終わらず、実用性はどこにありますか？
   - 土壌水分、照度、温度をもとに乾燥や水やり後の変化を検知し、チャットや Push 通知で知らせます。ユーザーは数値を読み解かなくても、今必要な世話に気づけます。

8. この仕組みは盆栽以外にも展開できますか？
   - できます。センサ入力、プロフィール、プロンプト、適正しきい値を変えれば、観葉植物、農作物、教育用栽培キット、ペット的な IoT デバイスにも展開できます。

9. システム全体で一番難しかった部分はどこですか？
   - センサ値を単に文章化するのではなく、会話履歴や性格設定と矛盾しない自然な返答に統合する部分です。数値、記憶、キャラクター性の優先順位をプロンプトとサービス層で調整しました。

10. 実装上、最も工夫した点はどこですか？
    - Go バックエンドで、プロフィール、最新センサ状態、画像診断、直近履歴、関連記憶を毎回動的に組み立てて Gemini に渡す構成にした点です。LLM 依存部分は `internal/llm` に抽象化し、ストリーミングやフォールバックも切り替えられます。

## センサ・ESP32関連

11. 使用しているセンサの種類は何ですか？
    - 実機コードでは BME280 で気温・湿度・気圧、BH1750 で照度、SEN0604 系の土壌センサーを RS485/Modbus 経由で土壌水分・土壌温度・EC・pH として取得します。バックエンドの主要値は土壌水分、照度、気温です。

12. 土壌水分はどのように測定していますか？
    - 実機では土壌センサーから得た `soil_moisture_percent` を優先して使います。バックエンドではこの値を正規の水分値として扱い、通常の `moisture_percent` より優先します。

13. 照度や気温の値はどの頻度で取得していますか？
    - デモ用 ESP32 ファームでは約 10 秒間隔で送信しています。本番想定では常時監視しつつ、10 分程度の定期送信または水分変化時の即時送信に調整します。

14. センサ値の誤差やノイズにはどう対応していますか？
    - ESP32 側でセンサー値の妥当性を確認し、土壌センサーが不自然な値を返した場合はデモ用の動的モック値に切り替えます。バックエンド側でも範囲外の値をクランプし、`sensor_status=invalid` として扱います。

15. センサ値の異常値はどのように扱っていますか？
    - 水分は 0 から 100%、照度は 0 以上、温度は -50 から 100 ℃の範囲に正規化します。範囲外があれば `invalid` として記録し、プロンプトでは「身体の感覚に乱れがある」と扱います。

16. 土壌水分の「乾いている／湿っている」の判定基準はどう決めていますか？
    - 現在はプロンプト上で 15% 以下をかなり乾燥、35% 以下を乾き始め、65% 以下を適度、85% 以下をしっとり、それ以上を水が多い状態として扱っています。乾燥イベントは 20% 未満に下がった瞬間を検知します。

17. 盆栽の種類によって適切な水分量は違うと思いますが、どう対応しますか？
    - 現状は共通しきい値でデモしています。本番では盆栽の種類や季節をプロフィールに持たせ、しきい値とプロンプトの身体表現を個体ごとに切り替えます。

18. センサのキャリブレーションは行っていますか？
    - デモ版では ESP32 コード内の固定値・センサー側の読み取り値で調整しています。アプリからの動的キャリブレーション UI は未実装ですが、本番では鉢や土ごとの乾燥・湿潤基準を登録できるようにします。

19. センサ値はリアルタイムで反映されますか？
    - 最新値は ESP32 の POST 後に Supabase PostgreSQL へ upsert され、フロントは 30 秒ごとに取得します。水やり・乾燥イベントは WebSocket でアクティブ画面へ即時通知します。

20. ESP32からSupabaseへの送信が失敗した場合はどうなりますか？
    - ESP32 は Supabase へ直接送らず、Go バックエンドの `POST /api/v1/sensor` に送信します。送信失敗時はシリアルログに HTTP ステータスやエラーを出し、次の送信周期で再試行します。

21. 通信が切れたときの対策はありますか？
    - ESP32 側は Wi-Fi が切れていれば再接続してから送信します。バックエンド側では最終更新から 15 分を超えると `stale` として扱い、会話でも「新しい感覚が届いていない」と表現します。

22. 電源はどのように供給していますか？
    - デモ版は常時給電を前提にしています。省電力化やバッテリー運用は本番化時の課題で、Deep Sleep と送信間隔の最適化で対応します。

23. 長期間運用した場合、センサの劣化は問題になりませんか？
    - 土壌に近いセンサーは劣化やドリフトが起きる前提で設計します。異常値検知、定期キャリブレーション、交換可能なセンサーモジュール化が長期運用時の対応です。

24. 水や土に近い環境で電子部品の安全性は大丈夫ですか？
    - 実装上は電子部品と水が直接触れない配置が前提です。本番化では防滴ケース、ケーブルの固定、低電圧駆動、センサー部のみ土に入れる構造にします。

## Goバックエンド関連

25. なぜバックエンドにGoを選んだのですか？
    - WebSocket、HTTP API、外部 API 呼び出し、DB アクセスを軽量に扱いやすく、単一バイナリで Fly.io に載せやすいためです。型が明確なので、センサー値やイベント判定の実装にも向いています。

26. Goバックエンドは具体的にどの処理を担当していますか？
    - 認証済み API、WebSocket、Gemini ストリーミング中継、プロンプト生成、センサー取り込み、イベント検知、Push 通知、pgvector 検索、会話履歴保存、画像診断連携を担当します。

27. フロントエンドからのリクエストはどのような流れで処理されますか？
    - フロントは Supabase JWT を付けて REST API または WebSocket に接続します。Go は JWT を検証し、ユーザー ID を確定してから DB や LLM にアクセスします。

28. センサ値、会話履歴、ユーザー発話はどのように統合していますか？
    - チャット時にプロフィール、最新センサー状態、画像診断、直近履歴 6 件、ベクトル検索で得た関連記憶 3 件を集めます。それらを system prompt にまとめ、ユーザー発話は user message として Gemini に渡します。

29. 動的プロンプトは毎回生成していますか？
    - はい。会話ごとに最新のセンサー状態、直近履歴、関連記憶、なじみ具合を取得して組み立てます。

30. プロンプトのテンプレートはどのように設計していますか？
    - 基本原則、個体の樹格、性格状態、会話の見立て、身体状態、画像診断、育ちの記録、手入れの記録、なじみ具合、長期記憶、直近会話、話し方モードの順に分けています。キャラクター性と実用情報が混ざりすぎないよう、役割ごとにブロック化しています。

31. プロンプトが長くなりすぎる問題にはどう対応していますか？
    - 直近履歴は 6 件、関連記憶は 3 件に制限しています。各履歴や記憶も文字数を切り詰め、長期記憶は会話全文ではなく 1 往復の要約として保存します。

32. Go側でセンサイベントを検知するロジックはどうなっていますか？
    - `SensorService.Ingest` で前回値と今回値を比較します。正常な値同士で、水分上昇または乾燥しきい値の跨ぎを検知したときだけイベント化します。

33. 水やりイベントや乾燥イベントはどのように判定していますか？
    - 水やりは 3 分以内に土壌水分が 20 ポイント以上上昇した場合です。乾燥は前回 20%以上だった水分が今回 20% 未満に下がった場合です。

34. 複数ユーザーや複数の盆栽に対応できますか？
    - ユーザーごとの分離は実装済みです。現状の `sensor_data` と `bonsai_profiles` は `user_id` 主キーなので 1 ユーザー 1 盆栽ですが、`bonsai_id` を追加すれば複数盆栽に拡張できます。

35. バックエンドの負荷が増えた場合、スケールできますか？
    - API と WebSocket は Go の軽量なサーバーとして水平スケール可能です。ただし現状の WebSocket Hub はインメモリなので、複数インスタンス化する場合は Redis Pub/Sub などでイベント配送を共有する必要があります。

36. APIキーや環境変数はどのように管理していますか？
    - バックエンドは `.env` または Fly.io secrets、フロントは `NEXT_PUBLIC_*` の公開可能な値のみを使います。Gemini API キー、Supabase Secret、VAPID Private Key、センサートークンはサーバー側に閉じます。

37. エラー発生時のログや監視はどうしていますか？
    - 現状は Go の `log` と HTTP/WebSocket のエラーレスポンスで確認します。Ready/Liveness として `/healthz`、`/readyz` があります。本番では構造化ログ、メトリクス、アラートを追加します。

## Gemini・LLM関連

38. なぜLLMにGeminiを選んだのですか？
    - ストリーミング生成と埋め込みを同じ Google Generative Language API 系で扱え、低遅延な Flash 系モデルを使いやすいためです。将来的な画像・マルチモーダル連携とも相性があります。

39. Gemini APIにはどのような情報を渡していますか？
    - system prompt には盆栽プロフィール、性格、来歴、最新センサー状態、画像診断、直近履歴、長期記憶、なじみ具合を入れます。user message にはユーザーの最新発話だけを入れます。

40. センサ値をどのように自然な文章へ反映していますか？
    - 数値を直接読ませず、バックエンド側で「根元は乾き始めている」「葉に届く光はやわらかい」などの身体表現に変換してからプロンプトに入れています。

41. LLMが間違った園芸アドバイスをしないようにする工夫はありますか？
    - 断定的な診断や大きな助言を避け、現在のセンサー値に基づいた小さな世話へつなげるプロンプトにしています。画像診断も「写真から見える手がかり」として扱い、病気や枯死を断定しない方針です。

42. 盆栽のキャラクター性はどのように制御していますか？
    - プロフィールの名前・性格・来歴、固定の bonsai DNA、なじみ具合、話し方モードで制御しています。口癖を固定するのではなく、反応の傾向として扱います。

43. 返答が毎回ぶれすぎないようにする工夫はありますか？
    - system prompt で返答長、禁止表現、センサ数値を直接言わないこと、過度な助言をしないことを明示しています。また直近で使った表現を検出し、繰り返しを避ける指示を入れています。

44. センサ値とユーザー発話が矛盾した場合、どちらを優先しますか？
    - 物理状態はセンサー値を優先します。ただしセンサーが `invalid` や `stale` の場合は断定せず、「感覚がはっきりしない」としてユーザーの観察も併せて扱います。

45. プロンプトインジェクション対策はしていますか？
    - ユーザー発話は system prompt と分離して user message として渡しています。また、盆栽として話す・設定値を出さない・AI と名乗らない等の上位指示を入れています。完全な対策ではないため、本番では入力検査や安全フィルタを追加します。

46. ユーザーが不適切な発話をした場合はどう処理しますか？
    - 現状は空文字と 2000 文字超の制限が中心です。外部操作や危険なツール実行はなく、LLM の返答も短い会話に限定しています。本番ではモデレーションやブロックルールを追加します。

47. LLMの応答速度はどれくらいですか？
    - ストリーミングなので、全体生成完了を待たずにチャンク単位で表示します。体感上は最初の数秒で返答が始まる設計で、フロント側でもなじみ具合に応じてタイピング速度を変えています。

48. API利用料金はどれくらい想定していますか？
    - 料金はモデル単価と利用回数で変わるため、審査時点では固定額として言い切りません。設計上は短文応答、履歴件数制限、Push の 2 時間クールダウン、Flash 系モデルでコストを抑えます。

49. Gemini APIが落ちた場合、代替手段はありますか？
    - Gemini モデルの優先順位を複数設定でき、429 や 503 では別モデルへフェイルオーバーします。API キー未設定時は開発用の `FallbackStreamer` で最低限の返答を返せます。

50. LLMなしでも最低限動く設計になっていますか？
    - はい。センサー表示、認証、履歴、Push 登録などは LLM なしでも動きます。会話生成と埋め込みはフォールバック実装がありますが、体験価値の中心は LLM 有効時です。

## pgvector・長期記憶関連

51. なぜ会話履歴をベクトル化する必要があるのですか？
    - 過去の会話を単なる時系列ではなく、意味的に近い記憶として取り出すためです。「前に水やりの話をした」「試験の話をした」などをキーワード完全一致なしで思い出せます。

52. pgvectorを使うメリットは何ですか？
    - Supabase PostgreSQL の中で通常テーブルとベクトル検索を一体で管理できる点です。小規模デモでは別のベクトル DB を立てずに RAG を実装できます。

53. どのタイミングで会話履歴を保存していますか？
    - ユーザー発話は LLM 呼び出し前に `chat_history` に保存します。アシスタント返答はストリーミング完了後に結合して保存し、その 1 往復を長期記憶として保存します。

54. どの単位でベクトル化していますか？
    - 1 往復単位です。「ユーザー: ... / 盆栽: ...」という要約テキストを作り、埋め込みを生成します。

55. 類似する過去の記憶は何件くらい取得していますか？
    - 現在は上位 3 件です。直近会話は別に 6 件取得します。

56. 関連度の低い記憶が混ざった場合はどうなりますか？
    - プロンプトでは「今回すぐに思い出せた記憶」として渡すだけで、必ず使う指示にはしていません。LLM は現在の発話や身体状態に合う場合だけ自然に使う設計です。

57. 古い記憶と新しい記憶の優先順位はどうしていますか？
    - 現状の長期記憶検索は類似度を優先しています。新しさによる重み付けは未実装で、本番では類似度と recency を組み合わせます。

58. ユーザーごとに記憶は分離されていますか？
    - はい。`bonsai_memories` は `user_id` を持ち、検索時も `where user_id = $1` で絞り込みます。RLS も有効化しています。

59. プライバシー面で会話履歴の保存は問題ありませんか？
    - 会話はユーザーごとに分離し、削除 API も用意しています。ただし本番では保存目的、保存期間、削除方法を明示し、個人情報を含む発話への配慮を追加します。

60. ユーザーが記憶を削除できる仕組みはありますか？
    - あります。プロフィール編集画面から会話履歴と長期記憶を削除でき、バックエンドでは `DELETE /api/v1/chat/history` が `chat_history` と `bonsai_memories` を削除します。

61. ベクトル検索の精度はどのように評価しますか？
    - 評価用の質問セットを用意し、期待する記憶が上位 3 件に入るかで確認します。さらに実ユーザーの「覚えてくれている感」があるかを主観評価で測ります。

62. 普通のキーワード検索ではなくベクトル検索を使う理由は何ですか？
    - 会話では同じ意味でも表現が変わるためです。「水をあげた」「潤った」「乾き」などを意味的に近い記憶として拾える点がベクトル検索の利点です。

## Supabase・DB設計関連

63. Supabaseを選んだ理由は何ですか？
    - Auth、PostgreSQL、RLS、pgvector をまとめて使えるためです。少人数開発でも認証・DB・ベクトル検索の土台を早く作れます。

64. PostgreSQLにはどのようなテーブルがありますか？
    - `bonsai_profiles`、`sensor_data`、`chat_history`、`bonsai_memories`、`push_subscriptions`、`bonsai_diagnoses` があります。プロフィール、最新センサー、短期履歴、長期記憶、Push 宛先、画像診断結果を分けています。

65. センサ値と会話履歴はどのように紐づいていますか？
    - `chat_history` には発話時点の `sensor_snapshot` を JSON として保存します。これにより、過去の発話がどの身体状態の時に行われたかを追えます。

66. データ量が増えたときの保存期間や削除方針はありますか？
    - 現状はユーザー操作による履歴削除のみです。本番では古いセンサー履歴の集約、会話履歴の期間制限、長期記憶の要約・圧縮を入れます。

67. RLSなどのセキュリティ設定はしていますか？
    - はい。主要テーブルで RLS を有効化し、`auth.uid() = user_id` のポリシーを設定しています。バックエンド側でも JWT から得た user_id でアクセスを制限しています。

68. ユーザー認証はどのように行っていますか？
    - フロントは Supabase Auth のメール/パスワードと Google ログインに対応します。バックエンドは Authorization Bearer または WebSocket の `token` クエリから JWT を受け取り検証します。

69. Supabaseに直接ESP32から送る設計で問題はありませんか？
    - 本実装では ESP32 から Supabase へ直接送りません。ESP32 は Go バックエンドへ共有トークン付きで送り、DB の Secret やサービスロールはバックエンド側だけで扱います。

70. DB障害時の対策はありますか？
    - 現状は `/readyz` で DB 接続状態を確認し、API ではエラーを返します。本番ではリトライ、バックアップ、Supabase の可用性設計、ESP32 側のローカルキューが必要です。

## WebSocket・ストリーミング関連

71. なぜHTTPレスポンスではなくWebSocketを使ったのですか？
    - LLM の生成途中をリアルタイムに表示でき、さらにセンサーイベントを画面へ自発的に流せるためです。チャットとイベント通知を同じリアルタイム経路で扱えます。

72. Geminiのストリーミング応答をどのようにフロントへ転送していますか？
    - Go が Gemini の SSE を読み取り、テキスト片を `reply_chunk` として WebSocket に流します。完了時は `reply_done` を送ります。

73. WebSocket接続が途中で切れた場合はどうなりますか？
    - フロントは切断状態とエラーメッセージを表示します。会話履歴は DB に保存されるため、再接続後に履歴を取り直せます。自動再接続は今後の改善点です。

74. 同時接続数が増えた場合の対策はありますか？
    - Go の WebSocket は軽量ですが、現状の Hub は単一プロセス内のメモリ管理です。本番で複数台にする場合は外部 Pub/Sub とロードバランサの sticky 設定を検討します。

75. ストリーミング表示によってユーザー体験はどう改善されますか？
    - 返答完了までの待ち時間を短く感じられます。盆栽が言葉を選んでいるような体験になり、無機質な API 応答より会話感が出ます。

76. 生成途中の文章を表示することで誤表示のリスクはありませんか？
    - リスクはあります。現状は短文かつ安全なプロンプトで抑えていますが、本番ではセンシティブな応答は生成完了後に検査してから出す設計も検討します。

77. ストリーミング中にユーザーが次のメッセージを送った場合はどう処理しますか？
    - フロント側で送信ボタンと候補文を無効化し、1 回の応答が終わるまで次を送れないようにしています。バックエンドも 1 接続内で順番に処理します。

## Push通知・自発メッセージ関連

78. どのような条件でPush通知を送りますか？
    - 水やり検知と乾燥検知です。水分が 3 分以内に 20 ポイント以上上昇した場合、または 20% 未満へ下がった場合にイベントを作ります。

79. 通知の頻度が多すぎる問題にはどう対応しますか？
    - 同じイベント種別は 2 時間のクールダウンを設けています。直近のイベント履歴を `chat_history` から確認して、連続通知を避けます。

80. 水やり後の変化はどのように検知しますか？
    - 前回の `sensor_data` と今回の値を比較し、正常値同士で水分差が 20 ポイント以上、かつ記録時刻の差が 3 分以内なら水やりと判定します。

81. 乾燥通知と通常会話でプロンプトは分けていますか？
    - 分けています。通常会話は長い system prompt を使い、センサーイベントは水やり用・乾燥用の短い専用プロンプトで 20〜60 文字程度の通知文を生成します。

82. Push通知の文章もGeminiで生成する理由は何ですか？
    - 同じ「乾いています」でも、盆栽の名前、性格、なじみ具合に合わせて自然な言い方にするためです。通知も会話体験の一部として扱っています。

83. 通知がユーザーにとって迷惑にならない工夫はありますか？
    - クールダウン、短文、責めない表現を入れています。乾燥時も「水をくれないから悪い」ではなく、今できる小さな世話へつなげる文にしています。

84. 夜間や授業中など、通知を控える設定はありますか？
    - 現状は未実装です。本番では quiet hours、曜日・時間帯設定、緊急度ごとの通知抑制を追加します。

85. 通知の緊急度はどのように決めていますか？
    - 現状はイベント種別で決めています。乾燥は水分が 20% 未満に下がったタイミング、水やりは反応通知です。本番では水分低下の度合い、温度、経過時間で段階化します。

## フロントエンド・UI/UX関連

86. なぜチャットUIにしたのですか？
    - ユーザーが植物の状態を質問しやすく、世話や雑談を自然に続けられるためです。状態を見るだけでなく、話しかけて関係を積み上げる体験に向いています。

87. 画面設計で一番重視したことは何ですか？
    - チャット体験を中心にしつつ、センサー状態や通知設定にすぐアクセスできることです。アプリを開いた瞬間に、盆栽の名前、接続状態、会話欄が分かる構成にしています。

88. 盆栽側とユーザー側の吹き出しを分けた理由は何ですか？
    - 会話の主体を明確にし、ユーザーの発話、盆栽の返答、センサーイベントを区別するためです。イベントは通常の返答とは別ロールとして表示します。

89. センサ値を数値ではなく会話として見せるメリットは何ですか？
    - 初心者でも「乾いているから水が必要そう」と理解しやすくなります。数値だけでは行動に結びつきにくい情報を、世話のタイミングとして伝えられます。

90. 「情報」と「センサー」の切り替えでは何を表示しますか？
    - モバイルでは「情報」で表示言語や基本情報、「センサー」でデバイス ID、状態、照度、水分、気温、最終更新、水分固定などを表示します。

91. スマートフォンでの使いやすさはどう考えていますか？
    - PWA としてインストールでき、モバイルメニュー、通知設定、写真診断、チャット入力をスマホ前提で使えるようにしています。Service Worker で Push 通知も受け取れます。

92. 候補文を表示している理由は何ですか？
    - 初回ユーザーが何を聞けばよいか迷わないようにするためです。「今日の様子」「水やり」「光」など、センサー値が反映されやすい質問を置いています。

93. Streaming表示はユーザーにどう役立ちますか？
    - 待ち時間の不安を減らし、返答が生成されていることを視覚的に伝えます。なじみ具合に応じてタイピングの遅延や速度も変わります。

94. 高齢者や園芸初心者でも使いやすいUIになっていますか？
    - 数値を最小限にし、候補文と自然言語の返答で使えるようにしています。高齢者向けには文字サイズ、音声入力、通知設定の簡略化が今後の改善点です。

95. センサ値のグラフ表示はありますか？
    - 現状はありません。現在の DB はユーザーごとの最新値を保持する設計なので、履歴グラフを出すには時系列センサーテーブルを追加します。

96. 画面上で異常状態をどのように伝えますか？
    - センサー状態として `正常`、`更新待ち`、`一部異常` などを表示します。チャットでは `stale` や `invalid` を身体感覚の乱れとして反映します。

97. UIの色やデザインは盆栽の世界観に合わせていますか？
    - はい。落ち着いた背景、葉・水・光を連想する色、PWA アイコン、チャット中心の静かなデザインにしています。

98. アクセシビリティは考慮していますか？
    - ラベル、`aria-label`、ボタン状態、モバイルメニューの Escape 対応などは入れています。今後はキーボード操作、コントラスト、スクリーンリーダー確認をさらに行います。

## 評価・実験関連

99. 実際にどれくらいの期間テストしましたか？
    - 現状はローカル環境、モックセンサー、実機 ESP32 コードでの短期動作確認が中心です。審査前には同じ鉢で数日単位の連続送信と水やり検知を確認する予定です。

100. センサ値と実際の盆栽状態はどれくらい一致しましたか？
     - 現時点では定量評価中です。デモでは土壌水分の上下、水やり後の急上昇、乾燥方向の変化がプロンプトと通知に反映されることを確認対象にしています。

101. ユーザーが水やりを忘れにくくなる効果は測定しましたか？
     - まだ長期のユーザー実験は未実施です。評価では、通知前後の水やり実施率、アプリ起動頻度、乾燥状態の継続時間を比較します。

102. 会話によって植物への愛着が増えるか検証しましたか？
     - まだ定量検証はこれからです。会話前後のアンケート、継続日数、ユーザーが自発的に話しかけた回数で評価します。

103. LLMの返答品質はどのように評価しましたか？
     - 実装上はセンサー状態が反映されているか、断定的な園芸診断をしないか、短い返答になっているか、キャラクターが崩れないかを確認しています。今後は評価用プロンプトセットで点数化します。

104. 従来の通知アプリと比べてどのような改善がありますか？
     - 「水をあげてください」という一方向通知ではなく、世話の結果に対して盆栽が反応します。これにより通知が作業指示ではなく、関係性のフィードバックになります。

105. 技術審査で見せられるデモはどこまで動きますか？
     - ログイン、プロフィール設定、WebSocket チャット、センサー値表示、モックまたは ESP32 からのセンサー送信、水やり・乾燥イベント、Push デモ、画像診断を見せられます。実機接続は環境に依存するため、モックセンサーでも同じ API フローを再現できます。

## 事業性・展開性

106. この技術はどの市場に展開できますか？
     - 家庭向け植物管理、教育用栽培キット、高齢者の生活支援、店舗・オフィスの植物管理、園芸コミュニティ向けサービスに展開できます。

107. 盆栽以外の植物にも使えますか？
     - 使えます。植物種ごとの適正水分、光、温度のしきい値とプロンプトを差し替えることで対応できます。

108. 家庭向け以外に、教育・福祉・店舗などへの展開は考えていますか？
     - 考えています。教育では植物の観察記録、福祉では会話と世話による生活リズム支援、店舗では植物管理と接客体験として展開できます。

109. ハードウェア込みで販売する想定ですか？
     - 最初は ESP32 とセンサーを組み合わせたキット販売が現実的です。量産時は防滴ケース、簡単セットアップ、交換可能なセンサー構成が必要です。

110. 月額課金モデルは考えていますか？
     - 考えられます。基本機能は無料または買い切り、長期記憶、画像診断、複数鉢管理、通知履歴、家族共有を月額にする設計が可能です。

111. LLM API費用をどう回収しますか？
     - 月額課金、利用回数上限、短文生成、安価なモデル優先、通知生成の頻度制限で回収します。ヘビーユーザー向けにはチャット回数や画像診断回数で段階課金にします。

112. 大量生産する場合の課題は何ですか？
     - センサー個体差、キャリブレーション、Wi-Fi 設定、電源、防水、サポート、ファームウェア更新です。特に土壌センサーのばらつき対策が重要です。

113. 競合サービスと比べた強みは何ですか？
     - センサーデータを単なる通知ではなく会話と記憶に接続している点です。植物管理、AI キャラクター、IoT Push 通知を一つの体験に統合しています。

114. ユーザーが継続利用する理由は何ですか？
     - 水やりや声かけでなじみ具合が変化し、過去の会話を少し覚えた返答が返るためです。世話の積み重ねが会話に反映されることが継続動機になります。

## 弱点を突かれそうな質問

115. これは単にChatGPT風のUIを植物に付けただけではありませんか？
     - 違います。LLM 単体ではなく、ESP32 の実センサー、イベント検知、Web Push、pgvector の長期記憶を組み合わせています。返答は現在の身体状態と過去の世話に基づいて変わります。

116. LLMがなくても、しきい値通知だけで十分ではありませんか？
     - しきい値通知だけでも最低限の管理はできます。ただ、それでは継続意欲や愛着が生まれにくいです。LLM は行動を促すだけでなく、世話が届いた体験を作るために使っています。

117. 盆栽が本当に話しているわけではないことに違和感はありませんか？
     - そこは誤解させない設計にします。あくまでセンサーと会話生成によるインターフェースですが、ユーザーが世話の変化を感じ取りやすくする表現として会話形式を使っています。

118. センサ値が間違っていたら、LLMの返答も間違いませんか？
     - そのリスクはあります。そのため範囲外や古い値は `invalid`、`stale` として扱い、断定的な助言を避けます。ユーザーの目視確認や写真診断も補助情報として使います。

119. 園芸知識の正確性はどう保証しますか？
     - 現状は一般的な小さな世話に限定し、病気や枯死の断定を避けています。本番では植物種ごとの監修データ、専門家レビュー、ルールベースの安全ガードを追加します。

120. ユーザーが通知を無視したら意味がないのでは？
     - 通知を無視する可能性はあります。ただ、会話履歴や乾燥状態が残るため、次に開いたときにも状態を伝えられます。本番では通知頻度や表現を最適化して無視されにくくします。

121. 通信環境がない場所では使えませんよね？
     - 現状はクラウド API 前提なので通信が必要です。本番では ESP32 側に一時キューを持たせ、通信復帰後にまとめて送る設計にします。

122. 高齢者向けならチャットUIは本当に適していますか？
     - 高齢者全員に最適とは限りません。チャットに加えて候補文、音声入力、通知タップで開ける導線を用意することで、入力負担を下げます。

123. 盆栽の育成は種類や季節で違いますが、そこまで対応できますか？
     - 現状は共通ロジックです。本番では種類、季節、地域、屋内外、鉢サイズをプロフィール化し、しきい値と助言を切り替えます。

124. LLMのAPIコストが高くなったら継続できますか？
     - 短文化、安価なモデル、ローカルルール通知、キャッシュ、回数制限で抑えます。重要な通知はルールベースでも動くため、全機能を LLM に依存させません。

125. 技術的に一番リスクが高い部分はどこですか？
     - 実機センサーの安定性と、LLM の返答品質です。センサーは異常値検知とキャリブレーション、LLM はプロンプト制御・フォールバック・評価セットでリスクを下げます。

## デモで聞かれそうな質問

126. 今表示されている返答には、どのセンサ値が反映されていますか？
     - 最新の土壌水分、照度、気温、センサー状態が反映されています。画面上のセンサー欄に同じ値が表示され、バックエンドではそれを身体状態の文章に変換してプロンプトへ入れています。

127. この返答は毎回同じになりますか？
     - 完全には同じになりません。LLM 生成なので表現は揺れますが、同じセンサー状態、同じプロフィール、同じ履歴なら意味は近くなるように制御しています。

128. 過去の会話記憶はどこで使われていますか？
     - チャット時にユーザーの最新発話を埋め込み、`bonsai_memories` から関連する過去の 1 往復記憶を上位 3 件取得して system prompt に入れます。

129. 水をあげたら画面や通知はどう変わりますか？
     - 土壌水分が 3 分以内に 20 ポイント以上上がると水やりイベントになります。画面には WebSocket でイベントメッセージが流れ、Push 購読があればスマホにも通知されます。

130. センサ値を手動で変えた場合、返答は変わりますか？
     - 変わります。フロントには水分固定機能があり、手動値を反映すると `sensor_data` の水分値が変わり、次のチャットプロンプトにも反映されます。

131. 通知は実際にスマホへ届きますか？
     - ブラウザが Web Push に対応し、通知許可と VAPID 設定が揃っていれば届きます。デモ通知を送る API も実装済みです。

132. フロントとバックエンドの通信はどこで確認できますか？
     - REST はブラウザ DevTools の Network、WebSocket は Network の WS フレームで確認できます。バックエンド側は Gin ログと Go のログで確認できます。

133. WebSocketで送られているデータ形式は何ですか？
     - クライアントからは `{"type":"message","text":"..."}` です。サーバーからは `reply_start`、`reply_chunk`、`reply_done`、`error` が JSON で送られます。

134. Supabaseにはどのようなデータが保存されていますか？
     - プロフィール、最新センサー状態、会話履歴、長期記憶ベクトル、Push 購読、画像診断結果です。チャット履歴には発話時点のセンサースナップショットも残します。

135. エラー時の画面表示はどうなりますか？
     - 認証、センサー取得、WebSocket、Push、画像診断のエラーは画面上にメッセージとして表示します。WebSocket エラーは system メッセージとしてチャット欄にも出ます。

## 技術深掘りで来そうな質問

136. プロンプトの具体例を見せてもらえますか？
     - 構造は「基本原則」「この個体の樹格」「今日の性格」「会話の見立て」「今日の身体」「画像診断」「育ち」「手入れ」「なじみ具合」「長期記憶」「直近会話」「話し方」です。例えば水分 12% なら「根元はかなり乾いていて、言葉にも少し力が入りにくい」という身体状態が入ります。

137. DBスキーマを説明してください。
     - `bonsai_profiles(user_id, name, personality, backstory, tone_mode, bond_score)`、`sensor_data(user_id, device_id, moisture_percent, light_lux, temperature_celsius, sensor_status, raw_payload)`、`chat_history(user_id, role, content, sensor_snapshot)`、`bonsai_memories(user_id, summary, embedding vector(3072))`、`push_subscriptions(user_id, endpoint, subscription)`、`bonsai_diagnoses(user_id, health_score, ratios...)` です。

138. シーケンス図で処理の流れを説明できますか？
     - チャットでは、ユーザー送信、JWT 検証、プロフィール・センサー・履歴取得、ベクトル検索、Gemini ストリーミング、WebSocket 転送、履歴保存、長期記憶化の順です。センサーでは、ESP32 POST、トークン検証、最新値保存、イベント検知、LLM 通知文生成、WebSocket と Push 送信の順です。

139. センサ値からイベントを検知する条件式を説明してください。
     - 水やりは `current.recorded_at - previous.recorded_at <= 3分` かつ `current.moisture - previous.moisture >= 20` です。乾燥は `previous.moisture >= 20` かつ `current.moisture < 20` です。どちらも `sensor_status=normal` の場合だけ発火します。

140. ベクトル検索のSQLを説明してください。
     - `bonsai_memories` を `user_id` で絞り、`embedding <=> query_embedding` の距離で昇順に並べます。類似度は `1 - distance` として返し、上位 3 件をプロンプトに入れます。

141. WebSocketのメッセージ形式を説明してください。
     - 送信は `type=message` と `text` です。受信は開始時 `reply_start`、生成中 `reply_chunk`、完了時 `reply_done`、失敗時 `error` で、センサーイベントの場合は `source=sensor_event` と `event` が付きます。

142. Gemini APIのストリーミング処理はどのように実装していますか？
     - `streamGenerateContent?alt=sse` を呼び、SSE の `data:` 行をスキャンします。各 candidate の part text を取り出し、WebSocket の chunk としてそのままフロントへ送ります。

143. Push通知の送信フローを説明してください。
     - フロントで Service Worker を登録し、Push Subscription を取得して DB に保存します。イベント発生時に Go が購読情報を読み、VAPID キー付きで webpush-go から通知サービスへ送ります。

144. 認証とユーザー分離の仕組みを説明してください。
     - フロントは Supabase Auth の JWT を持ち、バックエンドは JWT を検証して user_id を決定します。DB も `user_id` を持ち、RLS とバックエンドの where 条件でユーザー間のデータを分離します。

145. 本番運用時の構成図を説明してください。
     - フロントは Vercel の Next.js/PWA、バックエンドは Fly.io の Go API、DB は Supabase PostgreSQL + pgvector、AI は Gemini、Push は Web Push、ESP32 は Go API へ HTTPS POST する構成です。スケール時は WebSocket Hub を外部 Pub/Sub 化し、センサー履歴と監視基盤を追加します。
