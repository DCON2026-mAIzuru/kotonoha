# Kotonoha デモ構成案

このメモは、技術審査会のライブデモと、本戦発表用のデモ動画を分けて整理する。  
結論として、審査会では「センサー値が変わる → バックエンドがイベント検知する → 会話・通知が変わる」という技術の因果関係を短く見せる。本戦動画では「盆栽の世話が会話として返ってくる体験」を先に見せ、その後に技術構成を補足する。

## 技術審査会デモ

### 目的

審査員に見せるべき中心は、画面の完成度よりも「実世界の状態が AI 会話と通知に接続されていること」。  
単なるチャット UI ではなく、ESP32 またはセンサーシミュレーターから入った値が、Go バックエンド、Supabase、Gemini、WebSocket、Web Push まで流れることを見せる。

### 推奨構成

| 役割 | 構成 |
|---|---|
| 操作用 PC | フロントエンド画面、バックエンドログ、必要なら Supabase テーブルを表示 |
| スマホ | 実際の利用画面、Push 通知の受信確認 |
| 盆栽・センサー | 可能なら ESP32 実機。通信不安定時は `hardware/simulator/sensor_simulator.py --demo` |
| 予備 | 事前録画した水やりイベント動画、固定済みスクリーンショット |

当日は「実機を見せる」ことに価値があるが、成功率を優先する。実機 ESP32 は机上に置き、ライブではシミュレーターを使ってもよい。説明では「実機と同じ `POST /api/v1/sensor` を叩いているため、バックエンド以降の流れは同一」と言えばよい。

### 画面配置

- メイン画面: スマホサイズの Kotonoha チャット画面
- 補助画面: PC のターミナルでセンサー送信ログ
- 必要時のみ: Supabase の `sensor_data` またはバックエンドログ

審査会では画面を増やしすぎない。基本はアプリ画面を見せ、技術質問が来たときだけログや DB を開く。

### 3 分デモ台本

1. 導入 20 秒
   - 「Kotonoha は、盆栽のセンサー値を会話と通知に変換するシステムです」
   - 「現在は土壌水分、照度、気温をコンテキストとして扱っています」

2. 通常会話 40 秒
   - フロントで盆栽に「今日の調子はどう？」と聞く
   - センサー状態が反映された短い返答を見せる
   - 補足: 最新センサー、プロフィール、会話履歴、長期記憶を Go バックエンドで組み立てて Gemini に渡している

3. 水やりイベント 60 秒
   - `python sensor_simulator.py --demo` を実行、または実機センサーで水分上昇を再現
   - 乾燥気味の値が送信されたあと、水やり後の値が送られる
   - フロントのセンサー表示、チャット上のイベント反応、Push 通知を見せる

4. 技術構成 40 秒
   - 「ESP32 は Supabase に直接書かず、Go API に送っています」
   - 「Go 側で水分差分を判定し、イベントになった場合だけ WebSocket と Push に流します」
   - 「会話履歴は pgvector で長期記憶化し、次回以降の返答に使います」

5. 割り切りと拡張 20 秒
   - 「デモ版ではしきい値は共通ですが、本番では樹種・季節・鉢ごとに変えます」
   - 「実機が不安定な場合も、同じ API 経路を通るシミュレーターで再現できます」

### 5 分デモ台本

3 分版に加えて、次を入れる。

- プロフィール設定: 盆栽の名前・性格が返答に反映されること
- 長期記憶: 過去に話した内容をもう一度聞き、関連記憶が返答に出ること
- 画像診断: 盆栽写真をアップロードし、見た目の手がかりを会話に反映すること

5 分以上ある場合でも、機能を全部見せるより「水やりイベント」を中心にする。Kotonoha の価値は、水やりという世話の行動に反応が返る瞬間で最も伝わる。

### デモ前チェックリスト

- [ ] フロントエンドにログイン済み
- [ ] プロフィール設定済み
- [ ] バックエンドの `/healthz` が正常
- [ ] Gemini API キーが有効
- [ ] Push 通知許可済み
- [ ] 水やりイベントのクールダウンに入っていない
- [ ] `SENSOR_USER_ID` がログイン中ユーザーと一致
- [ ] `SENSOR_SHARED_TOKEN` がバックエンドとシミュレーターで一致
- [ ] 実機 ESP32 が動かない場合のシミュレーター手順を準備
- [ ] ネットワーク不調時に見せる録画を準備

### 当日のリスク対策

| リスク | 対策 |
|---|---|
| 会場 Wi-Fi が不安定 | スマホテザリングを用意し、PC と ESP32 を同じ回線に寄せる |
| ESP32 が送信できない | シミュレーターで同じ API フローを再現する |
| Push が届かない | チャット画面の WebSocket イベントを主役にし、Push は補助扱いにする |
| LLM 応答が遅い | 先にセンサー表示とイベントログを見せ、ストリーミング開始を待つ |
| LLM 返答が微妙 | 事前に短く答えやすい質問を決めておく |
| 画面切り替えで混乱 | メインはスマホ UI、補助はログだけに絞る |

## 本戦発表用デモ動画

### 目的

本戦動画では、技術の説明より先に「なぜ使いたくなるのか」を見せる。  
審査員が最初の 20 秒で理解すべきことは、「盆栽の状態が、数字ではなく会話として返ってくる」「水をあげると反応が返る」という体験。

### 推奨尺

本編内で使うデモ動画は 60 秒から 90 秒が扱いやすい。  
長くても 120 秒以内にし、発表スライド側で技術説明を補う。

### 推奨ストーリー

1. 課題提示
   - 盆栽は毎日少しずつ状態が変わるが、初心者には水や光の判断が難しい
   - 数値だけの管理だと継続しにくい

2. 体験提示
   - ユーザーがスマホで「今日どう？」と聞く
   - 盆栽が現在の水分や光を反映して返答する

3. 世話の瞬間
   - 土が乾いていることが会話で伝わる
   - ユーザーが水をあげる
   - センサー値が上がり、盆栽から反応が届く

4. 技術の裏付け
   - ESP32 センサー、Go API、Supabase、Gemini、pgvector、Push の構成図を短く出す
   - 「実世界の変化」「記憶」「会話」「通知」がつながっていることを見せる

5. 未来像
   - 樹種別のしきい値、複数鉢管理、家族共有、教育・福祉・店舗への展開を一言で示す

### 90 秒動画構成

| 秒数 | 映像 | 伝えること |
|---:|---|---|
| 0-8 | 盆栽とスマホを同じ画角に置く | 植物管理ではなく、盆栽との関係性を見せる |
| 8-20 | アプリで「今日の調子はどう？」と入力 | 会話 UI の分かりやすさ |
| 20-35 | センサー状態つきの返答がストリーミング表示 | センサー値が会話に反映される |
| 35-50 | 水やりの手元を撮る | 実世界の行動 |
| 50-65 | 水分値上昇、イベント反応、Push 通知 | 行動に対して盆栽が反応する価値 |
| 65-78 | システム構成図を重ねる | 技術の接続関係 |
| 78-90 | 盆栽とスマホの引き画、最後の一言 | 継続した世話の体験として締める |

### 撮影構成

| カット | 内容 | 注意 |
|---|---|---|
| A | 盆栽、ESP32、スマホの引き画 | 最初に「実物がある」ことを伝える |
| B | スマホ画面のスクリーン録画 | 文字が読めるように明るさと拡大率を調整 |
| C | 水やりの手元 | センサー値の変化とつながるよう、直後に画面へ切り替える |
| D | Push 通知が届く瞬間 | 通知文は短く、読み切れる秒数を確保 |
| E | 構成図・ログの短い挿入 | 技術審査用ではなく、一般審査員にも分かる粒度にする |

スマホ画面をカメラで直接撮ると反射やピントずれが起きやすい。アプリ画面はスクリーン録画を使い、盆栽や水やりの映像と編集でつなぐのがよい。

### ナレーション案

> Kotonoha は、盆栽の状態を会話に変える IoT AI システムです。  
> 土壌水分、光、温度を ESP32 で取得し、バックエンドが現在の状態と過去の記憶を組み合わせて返答を生成します。  
> 乾いているときは、盆栽自身の言葉で気づかせてくれます。  
> 水をあげるとセンサー値が変化し、その変化を検知してチャットや通知で反応します。  
> 数値を読む管理ではなく、世話が届いたと感じられる体験を作ります。

### 動画で見せるべき優先順位

1. 水やり後に反応が返る瞬間
2. センサー状態が返答内容に反映されること
3. Push 通知で盆栽側から話しかけること
4. 過去の会話を少し覚えていること
5. 画像診断や詳細ログ

画像診断や長期記憶は強い機能だが、動画内で詰め込みすぎると主題がぼやける。本戦動画の主役は「実世界の世話が会話に変わる瞬間」に置く。

### 撮影前チェックリスト

- [ ] 返答が短く自然になる質問を 3 つ決める
- [ ] 水やり前後のセンサー値を確実に再現できる状態にする
- [ ] Push 通知文が画面内で読み切れる長さになっている
- [ ] スマホ画面録画、実写カメラ、音声の同期方法を決める
- [ ] 個人情報、API キー、Supabase URL、トークンが映らないようにする
- [ ] 通知やログに本名・メールアドレスが出ないアカウントを使う
- [ ] 予備として、シミュレーター版の水やりイベントも録画しておく

## 使い分け

| 場面 | 主役 | 見せ方 |
|---|---|---|
| 技術審査会 | 技術の因果関係 | ライブ操作、ログ、API フロー、イベント検知 |
| 本戦発表動画 | 体験価値 | 盆栽、スマホ、水やり、通知の一連の物語 |

技術審査会では「どう動いているか」を説明できる構成にする。  
本戦動画では「なぜこの体験が必要か」が先に伝わる構成にする。
